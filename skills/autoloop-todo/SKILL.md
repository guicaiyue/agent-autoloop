# 进度清单：一条消息，每轮更新

一件事有很多步、要跨很多轮时，人只想知道「现在到哪了」。做成一张**始终是同一个 key 的通知卡**：第一轮发出去，之后每轮换掉它的文字，Telegram 上永远是那一条消息被改写，不会堆成十张。

## 用什么字段

回执里的 `notice`，`key` 固定不变：

```json
{"notice":[{"key":"todo","title":"设置页卡顿 · 6/19","text":"✅ reapply 分流\n✅ 签名比较\n⏳ 遮罩按名增删\n⬜ 客户端拆 load"}]}
```

同一个 `key` 的通知还开着时，中台换掉它的标题和正文、版本号加一，通道据此原地改那条消息（`docs/protocol.md` 的「`notice` 的 `key`」一节）。关掉之后再写是新的一张。

**`key` 的规则**：整件事从头到尾只用一个，别每轮换。换一次就多一条消息，等于没做。建议用事项名，如 `"cdx-settings-lag"`、`"story-migrate"`。

## 版式的硬限制

通道把卡片切成三块（见节点 195 的定稿）：标题行 / 正文 / 结论条。

- **标题 ≤40 字**，把进度计数放这儿：`设置页卡顿 · 6/19`
- **正文 ≤1500 字**，超了通道**直接截断**，不会报错。19 条带描述必定破线，所以你只放**当前这一屏**
- 结论条 ≤120 字，结案时才出现

正文只放正在做和接下来两三条，做过的压成一行计数：

```
✅ 已完成 5 项（reapply 分流、签名比较、遮罩增删、load 拆分、busy 分流）
⏳ 正在做：成员勾选防抖
⬜ 接下来：e2e 请求计数、真机验收
❌ 卡住：无
```

详细的 19 条写在仓库里（`docs/plan/<事项>.md`），卡上只给指针：「全部 19 条见 docs/plan/settings-lag.md」。

## 每一轮怎么做

1. **先读这一轮的 `detail`**，它是派活的人写的这一轮要做什么。`detail` 说的就是全部范围，别自己扩大。
2. **再看 `open`**：还没结的卡片里有 `key` 是你那个的那张，读它的正文，那是上一轮留下的进度。**接着它改，不要重头数一遍**。
3. **干活**，只做 `detail` 说的。
4. **更新卡**：回执里写同一个 `key`，`title` 换新的计数，`text` 换新的那一屏。
5. **做完了就结案**：用 `resolve` 结掉这张卡（`{"card": <open 里的编号>, "reason": "19/19 全部完成，npm run verify 全绿"}`），别留着一条永远显示「6/19」的旧消息。

**`open` 里的卡不等于这一轮的活。** 它只是告诉你进度到哪了。如果 `detail` 只要一件事（「发一张卡」「确认一下」），做完那件就结束，**不要因为卡上写着 19 条就自己开始干那 19 条**。那是下一轮或别人的事。

## 一条规矩：卡上的字要能让人判断

标题里的计数是给人看的，正文里每一项都要是**他看得懂的结果**，不是内部动作：

- 好：`✅ 保存不再卡：从 314ms 降到 25ms`
- 差：`✅ lib/apply.js:215 加签名比较`

写「做成了什么」，不写「改了哪个函数」。这一条和 `worker/contract.ts` 对结论第一行的要求是同一个理由。

## 结案之后

清单结案了，这条消息就停在最后一次的状态。下一件新活要用同一个 `key` 也行——上一张已经 closed，会发新的。但别在同一件事中间关掉再开，那样手机上会出现两条。

## 不要做的

- 不要每轮发新的 `key`，那是堆消息
- 不要把 19 条全塞进 `text`，会被截断，而且手机上要滑很久
- 不要用 `ask` 做进度卡：`ask` 是等人拍板的，同一个 key 还开着时不会再发，进度就停了
- 不要在 `fyi: true` 的通知上做进度：`fyi` 一创建就 closed，下一轮会发新的一张
